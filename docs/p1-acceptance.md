# P1の結合テストと運用確認

P1の結合テストは、空のローカルD1から実際のWorker APIを順に呼び出す。候補の作成や審査結果をSQLで直接投入しない。探索の入口にはDraft 6の「URL単体」を使い、キーワード・チャンネル・再生リストの自動探索と過去作品探索は、このテストの実装済み範囲に含めない。

## ローカルで再現する確認

```sh
node --test tests/p1.integration.test.js
```

| 確認する流れ | 合格条件 |
|---|---|
| URL単体の発見→取得→人による審査→公開承認→公開結果記録 | 未審査の候補は公開できず、採用後に承認した作品とキューだけが公開用JSONへ入る |
| 取得不能の再確認→削除→削除版の公開結果記録 | 23時間間隔では削除せず、24時間間隔の正常な照会で取得不能を確認した後に作品・API情報・発見経路・関連キュー・旧公開本文を除去する。監査の公開状態を`pending`から`verified`へ更新する |
| 削除後の明示的な再発見 | 新しい内部IDの未審査候補となる。削除した作品IDや古いキューIDを再利用して公開しない |
| 重複発見・API情報更新・同時編集 | 発見経路を重複保存せず、別の経路を保持する。審査結果・メモ・手動確認日時を自動処理で変更しない。古い世代の編集を拒否する |
| API障害の継続→保持期限に基づく削除 | 通信障害や壊れた応答を動画取得不能として数えず、最終正常取得日時を延長しない。保持期限の72時間前には別の期限条件で削除する |
| 定期更新の中断→再開 | 未審査・保留・却下・採用のすべてを更新対象にする。失敗した作品を24時間待機させ、後続作品の処理を進める。次の実行ではD1の取得日時から残りを選択する |
| 公開結果不明→終了証拠に基づく復旧→再公開 | 不明のまま次の公開を開始しない。別の試行や不十分な終了状態を拒否する。信頼するデプロイ処理による復旧後も検証済みとは扱わず、新しい公開試行の結果を待つ |
| 権限分離 | 定期処理用トークンでは審査・公開承認・デプロイ結果記録をできない。デプロイ用トークンでは候補登録・審査・定期処理をできない |
| 保持日数を変更した環境 | Worker設定の保持日数が作品一覧・詳細にも渡り、短い期限で失効したAPI表示情報を返さない |

時刻の経過はテスト専用の入口から注入する。製品のWorkerには時刻を変えるAPIやテスト用ヘッダーを実装しない。YouTube応答もテスト専用の合成データであり、本番作品を削除しない。

この6件のテストはローカルMiniflareのD1で確認する。表の複数の条件を1件のテスト内で続けて検証する場合がある。公開先のHTTP照合、Artifactの許可ファイル、GitHub実行状況による復旧判定はPythonのデプロイテストで別途確認する。

開発依存パッケージの `npm audit` には、P0から使用しているMiniflare・sharp・undiciの依存経路でHighが3件報告されている。P1で追加したWorker実行時のnpm依存はないが、開発ツールの指摘は解消済みとは扱わない。依存更新と互換性確認は別途必要である。

## 本番導入後に残る運用確認

ローカルの合格と、GitHub Actions・Cloudflare・Pagesの実接続が動いたことは区別して記録する。

1. [導入手順](setup.md)に従い、追加migration、Worker、main、Secrets・有効化変数の順で反映後、定期処理workflowを手動で起動する。D1の実行結果とActionsの結果を照合する。
2. 公開要求があれば、公開Artifactが`library.json`と`queue.json`だけを含み、公開URLの両本文が最新版と一致することを確認する。D1の`verifiedRevision`が最新版になったことまで確認する。
3. 障害復旧は隔離した検証環境で確認する。処理中断後に再実行して残りを処理できること、旧公開処理が終わった証拠がない場合は新しい公開を開始しないことを確認する。本番公開を故意に壊す試験に置き換えない。
4. 定期実行を有効にした後、最初の`schedule`起動とその結果を確認する。Museが実行ID・最終結果・公開反映待ち・古い実行を読み取れることも確認する。

短時間のテストだけでは、数週間の無人運用や将来のスケジュール起動を実証したことにならない。実接続の実行ID・結果・確認時刻と、未確認の項目を導入記録へ残す。
